# Fixing diagnostics

Each diagnostic cites a stable rule and keeps its primary source location. Secondary
labels identify the supplied value, its origin and the receiving requirement when
those sites are available. `help` notes describe possible repairs; check the stated
conditions before editing. A JSON `fix` contains a half-open UTF-8 byte span and a
suggested replacement for a mechanical edit. Apply it only to the same source revision.

This reference is generated by `tools/generate-diagnostics.py`. The main sections
come from `crates/hirsel-diag/src/guidance.tsv`, the same repair guidance used by
diagnostics. More specific repairs in a diagnostic take precedence over the typical
fixes below. Related-rule subsections explain other uses of these ownership causes.

## MODE-4: Sendability

The value does not satisfy the receiving type's sendability contract.

Typical fix: For counted data, pass a `unique` value with sendable parts; remove local borrows or non-sendable handles from the payload. A `copy` does not prove sendability.

### CONC-5: Mutexes

A mutex needs a unique, sendable payload; its callback must hold no authority and return sendable data.

Typical fix: Build a unique payload before `mutex.create` and pass its ownership with `take value`. Keep `mutex.with` callbacks `uses {}`; perform I/O and synchronization outside them.

### CONC-6: Channels

A channel payload must be owned and sendable. A Receiver cannot be part of a channel payload.

Typical fix: Pass an owned sendable value with `take value` at its last use. For copyable counted data, `unique value` can remove sharing when allocation is permitted. Remove local borrows and Receiver parts from the payload.

## MODE-1: Local values

The value borrows storage that ends before the receiving value does.

Typical fix: Keep the result within its owner's scope, or declare the result `in x` when it borrows parameter `x`. For a borrowed non-Shared parameter, `copy x` still borrows the same storage.

## MODE-2: Uniqueness

The checker cannot prove the value and its required parts are unique here.

Typical fix: End live shares before this operation, or use `unique x` to obtain a deep unique copy of counted data. Deep copying may allocate and preserves arena placement; `copy x` shares storage.

### MEM-11: Shared graphs

Freezing requires a unique, inert graph containing no resources. Freeze and thaw may allocate.

Typical fix: Make copyable counted data unique before `shared.freeze`, and remove resource or authority-bearing parts. `copy value` shares storage and cannot prove uniqueness. An existing Shared root is copied with `copy`; recovering its unique contents requires `shared.thaw`.

## PROV-1: Brands

The value's brand differs from the required owner, or that owner's identity has ended.

Typical fix: Use a value created by the required owner. After moving or replacing an owner, recreate values branded by it before using them again.

## GEN-1: Structural bounds

An actual type lacks a structural property required by the generic operation.

Typical fix: For generic `T`, add the required bound to its declaration, for example `[T: copyable]` before copying `T`. For a concrete type, change the operand or operation to satisfy the named bound.

## LANG-7: Types

A type or value does not satisfy the type required at this site.

Typical fix: Make the operand and receiving annotation agree. For a non-exhaustive `match`, add arms for the missing values; guarded arms do not establish complete coverage.

## MEM-5: Allocation promises

An operation or cleanup may allocate inside an `@noalloc` function.

Typical fix: Use an operation whose signature promises `@noalloc`, and avoid allocating construction or cleanup in this body. Remove `@noalloc` from the enclosing signature if allocation is intended.

## PROV-4: Arena placement

The value's arena placement does not satisfy the receiver, or the arena ends too soon.

Typical fix: Keep the value inside `arena.with`, or declare the receiver `in a` for the correct arena `a`. `copy x` and `unique x` keep its placement; neither moves arena data to the heap.

## LANG-14: Reserved names

A reserved word appears where an ordinary identifier is required.

Typical fix: Rename this identifier and its references, for example to `value` or `result`; reserved keywords cannot be used as binding names.

## CAP-2: Authority

An operation lacks its typed capability, or a value's authority exceeds an `inert` or declared authority bound.

Typical fix: Pass the operation's explicit capability argument. An opaque type must declare the authority of its fields, for example `uses {Dir}` for a `Dir` field. For an `inert` receiver, remove authority-bearing captures or payloads, or change the receiver's bound; `uses` does not grant a capability.

## OWN-2: Moves and availability

The value was moved, was not initialized on every path, or was borrowed where ownership is required.

Typical fix: Use the value before its `take`, or initialize it on every reaching path. To pass an owned binding to a `take` parameter at its last use, write `take x`; if a copyable value must remain available, pass `copy x` instead.

## LANG-12: Argument labels

The call's labels or positional arguments do not match the declared parameters or fields.

Typical fix: Supply every declared argument exactly once using its declared label, for example `Point(x: 1, y: 2)` for fields `x` and `y`; remove unknown or repeated labels.

## LANG-2: Expected types

This expression lacks enough type information at the point it is checked, or is not permitted as a value in this position.

Typical fix: Give the expression a written type, qualify its constructor, or suffix a numeric literal, for example `let n: u64 = 1` or `1u64`. Generic arguments must be determined from the declared signature.

## SEM-3: Literals and formatting

A literal, escape or interpolation does not satisfy its literal or formatting contract.

Typical fix: Escape special characters, for example `\n`, `\"` or `\\`. For a custom interpolated type, provide `@format` with `fn(value: T, mut out: List[u8]) -> ()` for that type.

## OWN-1: Borrowed storage

The operation tries to move from or write through a read-only borrow.

Typical fix: Read the borrowed value, or copy it first with `copy x` if its type is copyable. If the function must consume or mutate the caller's storage, declare its parameter `take x` or `mut x` and update callers accordingly.

## LANG-4: Names

A name is missing, ambiguous, or conflicts with an existing declaration.

Typical fix: Use the exact declared name and module path. Disambiguate with a full `package@version/module/name` path; rename a conflicting binding and its references.

## LANG-13: Patterns

The pattern is invalid, refutable in an irrefutable position, or unreachable.

Typical fix: Use `match` or `let P = value else { return ... }` for a refutable pattern. Bind the same names with the same types and modes in every alternative, and remove unreachable alternatives.

## CLO-3: Task captures

A task capture must own sendable content and cannot borrow the caller's local storage.

Typical fix: Capture owned sendable data with `take x` at its last use, or copy a copyable sendable value with `copy x`. Remove scoped capabilities and borrowed local content from the task's captures.

## CAP-1: Capability arguments

The operation requires authority that has not been passed to it.

Typical fix: Add the declared capability parameter and pass it explicitly at this call. Forward that capability from the caller; a `uses` clause describes authority but does not create it.

## CAP-3: Restricted callbacks

The callback's authority exceeds the scope-forming operation's permitted authority.

Typical fix: Remove the prohibited capture or operation from the callback, or perform it outside the restricted scope using an explicitly passed capability.

## CLO-4: Escaping closures

The escaping closure's captures or authority do not satisfy its declared contract.

Typical fix: Own the escaping captures and keep them global. If the callback is permitted to use capability `net`, include `uses {net}` in its signature and pass the capability explicitly; otherwise remove that capture.

## OWN-4: Counted copies

A counted copy shares storage; a warning identifies an unnecessary copy at a borrowing call's last use.

Typical fix: To keep a copyable counted value available while passing an owned argument, write `copy x`. For the redundant-copy warning, pass `x` directly to the borrowing callee at its last use.

### OWN-5: Noncopyable values

Resources, task handles, Receivers, once closures, arenas, regions and values containing them can only be moved or borrowed.

Typical fix: Borrow the value when the callee only reads it. To transfer an owned value at its last use, write `take value`; change a borrowed parameter to a `take` parameter if the function must consume it. `copy value` cannot repair a noncopyable type.

## OWN-7: Published storage

Published Shared and region storage is immutable.

Typical fix: Read frozen contents with `shared.with`. To modify Shared contents, consume the owning handle with `shared.thaw(take value)` and handle its still-shared Error result before mutating the unique Ok value. Modify region contents before publication.

## LANG-8: Errors

A propagated error does not fit the enclosing error type, or an error mapper does not map it there.

Typical fix: Plain `?` injects only through the one arm whose payload is the propagated nominal error; otherwise name the arm with `? Arm`, map the error with a function `? f`, or handle it at the site.

### LANG-8: Plain ? with no arm

No arm of the enclosing error type has exactly one field whose type is the propagated nominal error. The diagnostic offers three repairs; only the first is a mechanical edit, and its JSON `fix` appends the arm to a declaration in the same file. When the error type is serializable, a note says that the arm changes its stored and wire schema (STORE-7, SER-2).

Typical fix: (a) Add the arm the fix proposes, such as `File(FileError)`; this changes the error contract of every function returning the type, so prefer it only when callers should see that failure. (b) Handle the error at the site with `match` or `let Ok(..) = .. else { .. }`. (c) Map it explicitly with `? C`, a function from the propagated error or an arm whose payload it is.

### LANG-8: Ambiguous plain ?

Two or more arms of the enclosing error type carry the propagated error. Each is a different role, such as `Storage(StoreError)` and `Unknown(StoreError)`, so plain `?` chooses none and there is no automatic fix.

Typical fix: Name the arm whose role fits this site: `? Storage` or `? Unknown`.

### LANG-8: Primitive errors

Plain `?` injects only nominal errors: a named type or a type parameter. A `String`, `Bytes` or other primitive, tuple, function or builtin error names no error domain.

Typical fix: Name the arm that carries it, such as `? Utf8` for a `Bytes` error, or map it with a function.

### LANG-8: Unconstructed error arms (warning)

No body of the package constructs this arm of one of its package-private error types, so callers match a failure that never happens. `pub` types are not linted, since other packages can construct their arms.

Typical fix: Remove the arm if nothing fails that way any more, updating the matches that name it, or construct it where that failure occurs.
