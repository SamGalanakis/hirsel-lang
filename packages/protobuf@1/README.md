# protobuf@1

Proto3 for Hirsel: the binary wire format, the canonical proto3 JSON mapping, the
well-known types, and `protoc@1`, a generator that turns `.proto` files into Hirsel
records, variants and functions. It is a package, not part of std. Programs depend on
it through their manifest:

```json
{ "manifest": "<path>/packages/protobuf@1/hirsel.json", "package": { "name": "protobuf", "version": "1" }, "expose": [] }
```

The package passes Google's conformance suite for proto3 binary and JSON
(`conformance/`; the pass count is recorded in `conformance/README.md`).

## Layout

- `wire.hir`: varints, zigzag, fixed32/64, length-delimited fields, packed
  repeated fields, skipping and keeping unknown fields, and tagged writers. Ported
  from protobuf-go `encoding/protowire` and prost `encoding.rs`.
- `json.hir`: the JSON runtime. It covers the number, string, bytes and enum rules of
  the proto3 JSON mapping; Timestamp, Duration and FieldMask text; `Any`; and the
  type registry. The rules follow protobuf-go `encoding/protojson`.
- `wkt.hir` (module `protobuf.wkt`): Timestamp, Duration, Any, Struct, Value,
  ListValue, NullValue, FieldMask, Empty and the wrappers, generated by `protoc@1`.
- `protoc/`: the generator, an ordinary Hirsel program.
- `conformance/`: the conformance testee and its adapter.

## Generating code

```
hirsel run packages/protobuf@1/protoc/hirsel.json --grants grants.json -- \
  [--grpc] [--external pkg=module]... <out.hir> <file.proto>...
```

The grants mount the directory holding the `.proto` files (and the output) at `""`.
Every listed file is generated into one Hirsel source, which belongs in one module
of its own. Imports must be listed too, or named with `--external pkg=module` when
another module already holds their code. The well-known types are built in and map
to `protobuf.wkt`. `--grpc` also emits service stubs over `packages/grpc@1`. The
generated source depends on `protobuf`, `std` and, with `--grpc`, `grpc`.

The generator runs as an ordinary program, not at compile time, because compile-time
code can neither read files nor publish types. Generated code is checked in after
`hirsel fmt <out.hir>`, since the generator does not wrap long lines itself.

Proto2 syntax, groups, extensions and `required` are rejected. Options other than
`packed` and `json_name` are ignored.

## Naming rules

- **Types.** A message `pkg.Outer.Inner` becomes the record `Outer_Inner`. Its
  fields are the proto field names. The last field, `unknown_fields: Bytes`, keeps
  unknown fields in wire order. A name that is a Hirsel keyword, a core type name,
  or (for fields) a generated local gets a trailing `_`: field `type` becomes
  `type_`, and oneof `result` becomes `result_`.
- **Field types.** Scalars map as `int32` → `i32`, `uint64` → `u64`, `sint32` →
  `i32`, `fixed64` → `u64`, `float` → `f32`, `string` → `String`, `bytes` → `Bytes`.
  Then:
  - A singular message field is `Option[M]`. It is boxed (`Option[box M]`) when its
    type can reach the containing message.
  - An `optional` scalar is `Option[T]`.
  - A `repeated` field is `List[T]`.
  - A `map<K, V>` field is `Map[K, V]`.
- **Oneofs.** A oneof `o` of message `M` is the variant type `M_o`, with one variant
  per member, each named after its field. The record field is `o: Option[M_o]`.
- **Enums.** An enum `E` is a variant type with one variant per value name, plus
  `Unrecognized(i32)` for open-enum numbers that are not declared. Aliases
  (`allow_alias`) share the variant of the first value with their number.
- **Functions.** Each is a prefix plus the type name:
  - For a message: `default_M`, `encode_M`, `decode_M`, `write_M(m, mut out)`,
    `read_M(data, depth)`, `to_json_M(m, registry)`, `from_json_M(value, options)`
    and `type_M` (its registry entry).
  - For an enum: `number_E`, `from_number_E`, `name_E`, `from_name_E`, `to_json_E`
    and `from_json_E`.
  - `message_types()` lists the registry entries of every generated message. Pass it,
    with `protobuf.wkt.message_types()`, to `protobuf.registry` for `Any`.
- **Helpers.** `writepart_M_K`, `tojsonpart_M_K`, `readpart_M_K` and `jsonpart_M_K`
  encode and decode chunk `K` of `M`'s fields, four fields (or oneofs) per chunk, and
  `jsonnumber_M` maps a JSON member name to its field number. They are generated
  private helpers. Chunking keeps the check time and memory of large messages near
  linear (`// GAP:` in `protoc/gen_emit.hir`).

## Semantics

- Decoding accepts packed and unpacked repeated scalars. It merges repeated
  occurrences of a singular message field. It treats a known field with the wrong
  wire type as unknown, and limits nesting to 100 messages.
- Encoding writes fields in number order and implicit-presence fields only when
  nonzero. It writes packed repeated scalars unless `[packed = false]`, and keeps
  unknown fields last.
- JSON output uses each field's JSON name. It writes 64-bit integers as strings,
  non-finite floats as `"NaN"`, `"Infinity"` and `"-Infinity"`, and bytes as
  standard base64. Input accepts both field names and JSON names, numbers given as
  strings, and both base64 alphabets with or without padding.
  `JsonOptions.ignore_unknown_fields` skips unknown members and enum names.
